Decision brief · Preview++ plugin architecture

Isolate every plugin, and let a speed test pick between app extensions and processes

Prefer B, every plugin as an ExtensionKit app extension embedded in the app, if a prototype shows a PDF and a text file opening at least as fast as Preview and TextEdit. It is the only option that can meet all five Musts: plugins draw full native UI in their own process, contributors add them through the repo, and the app keeps library validation on. Its open question is speed, which nobody has measured. If B is too slow, choose A, every plugin a separate process driving the app's native views. A is fast by estimate but leaves the app's own renderers (PDFKit, the text view) inside the app, which you'd have to accept or fix by moving rendering into a separate process. C is out for core formats because text would open about 70 ms slower than TextEdit. BASE fails the Must you set that even core plugins can't crash the app.

The goal: an open-source Preview replacement where every format, core included, is a plugin and no plugin can take the app down, while text, Markdown and PDF still open faster than Apple's apps.

Alternatives and comparison

BASE · Today's POC

Core plugins compiled into the app. Community plugins run as separate processes or web views.

A · Every plugin a process

Each plugin is a separate process that drives native components the app owns (text, PDF, table, Markdown, lists), plus a web view fallback. Raycast's model, extended to core formats.

B · Every plugin an app extension

Each plugin is an Apple ExtensionKit extension embedded in the app, drawing its own SwiftUI from a separate sandboxed process.

C · Every plugin a web view

Each plugin is HTML and JS running in WebKit's separate process, fed the file by the app.

Priorities: Must = required; Should = important but negotiable; Could = optional; Undecided = not confirmed. You confirmed rows 1 to 5 as Must and row 6 (external sources) as Could. "Community" means a plugin committed to the open-source repo; external sources are a consideration only. Dropped before comparison: in-process JavaScriptCore (Tinycast's model) and runtime-loaded native bundles, because both run plugin code inside the app.

Shared limits and assumptions

  • Every option assumes the Markdown renderer gets fixed. Today, large Markdown opens in 1,002 ms against TextEdit's 258 ms in all of them.
  • No option sandboxes plugins against misuse. Isolation here means crashes and hangs only; trust comes from repo review, as in Raycast.
  • All timings come from warm launches on one Apple M6 Mac running macOS 27.0.1. A and C speeds are estimates derived from the CSV plugin, and B has no measurement.
  • A and B can coexist: B for repo plugins with rich native UI, A or web views for external plugins later, if you decide to support them.

Next steps

  • Decides the choice: prototype B. Embed text and PDF plugins as ExtensionKit extensions in the lean host, then measure window time and content-ready with the existing harness against Preview and TextEdit. Also check resize lag, crash and hang recovery, and how commands and side panels cross XPC. This turns B-1 from Unknown into a result.
  • If B is too slow: choose A and resolve A-2. Either accept, as a concession, that the app's renderers (PDFKit, text view) can crash the app, or prototype a separate rendering process that sends pages back through shared memory.
  • Either way: fix the Markdown renderer (swift-markdown, parsed off the main thread), and add paging to the process protocol before any plugin sends large data.
  • Later: decide whether external plugin sources matter. If they do, B needs a second path (A or web views) next to it.
Supporting evidence and capability definitions

Evidence register

  • E1 · POC benchmarks: bench/results/results.md. Medians of 5 runs after a warm-up (3 for large files). Head-to-head figures are time from open -F -a to the first document window, polled from the window list the same way for every app.
  • E2 · Isolation test: bench/run.py isolation section. A crash or hang command was run in each CSV plugin variant after it loaded; the runner recorded whether the host survived.
  • E3 · Signing experiment: bench/results/signing.md. Hardened-runtime host signed with an Apple Development identity, run against same-team, ad-hoc and unsigned plugins, with and without disable-library-validation and quarantine flags.
  • E4 · Plugin model research: research/plugin-models.md. ExtensionKit facts come from Apple's documentation on displaying available extensions and from community write-ups (massicotte.org, insidegui/TextTransformer); the research tags blog-level claims.
  • E5 · Platform research: research/platform.md (library validation, Homebrew policy, default-app prompts).
  • E6 · Raycast: raycast.com/blog/how-raycast-api-extensions-work (Node process, JSON-RPC over stdio, React reconciler, JSON Patch, AppKit rendering).
  • E7 · Tinycast: github.com/abue-ammar/tinycast docs/features/extensions.md and docs/not-planned.md (in-process JavaScriptCore, SwiftUI rendering, compatibility stopped at about 80%).

Estimate inputs

A-1 adds the measured process overhead (55.5 minus 49.1 ms, small CSV) to BASE. C-1 adds the measured web overhead (138.0 minus 49.1 ms, small CSV) to the measured Preview++ window times (247 ms small text, 268 ms small PDF). Both assume the overhead doesn't depend on format.

Read the labels separately from priority

Supported provides the outcome under the row's conditions. Partially supported provides a limited outcome, with its limit stated. Unsupported is known not to provide the outcome. Unknown lacks the evidence needed to judge it.

An Unsupported Must blocks selection unless the requirement changes. A Partially supported Must needs explicit resolution or a confirmed concession. An Unknown Must must be resolved before choosing unconditionally. That is why the recommendation above is conditional.
